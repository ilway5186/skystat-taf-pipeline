# SkyStat TAF Ingestion Service

> **실시간 항공 기상 예보(TAF)를 주기적으로 수집하고 중복 없이 저장한 뒤, 다른 서비스에 발행하는 서비스**

## 1. 서비스 목적
실시간 기상 예보(TAF)를 수집하고, 전문의 유효성을 검사한 뒤 저장한다. 그 후 알람 서비스 등 타 서비스에 TAF 데이터를 발행한다

## 2. 역할과 책임
### 2.1 수집
- **역할:** 외부 API를 스케줄링해 최신 TAF 데이터를 수집한다
- **책임** 
  - 5분 주기로 외부 API를 호출하여 TAF 데이터를 수집한다
    - 대상 공항은 500~3,000개 내외로 서버 스펙 및 현업 운영 여건에 따라 조절될 수 있다
    - API 동시성은 30으로 시작해 조정해 나간다 (외부 API 서버 RTM 고려) 
  - polling 전략은 5분 주기 전수 폴링을 사용한다
    - 외부 API가 `updated-since`방식을 지원하는지 불확실 하므로 기본 전략으로 채택
    - 향후 개선 가능성 있음

### 2.2 검증
- **역할:** 수집된 TAF 데이터의 유효성을 검증한다
- **책임**
  - 수집된 TAF 응답 데이터가 정상적으로 파싱 가능한지 검증한다
  - 필수 값이 누락되지 않았는지 검증한다
  - TAF 전문 기반으로 고유 식별자인 `TafId`를 생성한다
    - id는 TAF 전문 내용을 기반으로 만든 SHA-256 해시 값이다 (길이 64)

### 2.3 저장
- **역할:** 수집된 TAF 데이터를 저장한다
- **책임**
    - 수집된 TAF 데이터가 이미 저장된 데이터인지 확인한다 (중복 검사)
    - 저장 시 발행을 위한 Outbox 레코드를 함께 기록한다
      - DB 저장과 Outbox 기록을 하나의 트랜잭션으로 처리

### 2.4 발행
- **역할:** 수집된 최신 TAF 데이터를 발행한다
- **책임**
    - 메시지 큐로 수집된 TAF 데이터를 발행한다
      - 최소 한 번 이상은(at least once) 반드시 발행되어야 한다 (→ Outbox 패턴 적용)
    - 발행 시각, 성공 여부, 실패 사유를 기록한다
      - 장애 발생 시 책임 소명을 위해 로깅은 필수
    - 발행 실패 시 재시도 한다

### 2.5 보관
- **역할:** 보관 기간이 지난 TAF 데이터는 삭제(혹은 S3같은 저장소로 이동) 시킨다 
- **책임**
    - TAF 데이터가 보관 기간(1달)을 초과했는지 검사한다
    - 보관 기간을 초과한 데이터는 적절한 조치를 취한다

## 3. 예상 부하 및 인프라 설계 기준
### 3.1 일평균 수집 데이터 수 
  - 일 최대 15,000건 가정
    - 대상 공항: 최대 3,000개 
    - TAF 기본 발부(일 4회)와 수정 예보를 고려
  - polling 주기: 5분
  - 평균 Outbound 호출량: 10 req/s
 
### 3.2 서버 환경
  - Contabo VPS20 (6vCPU Cores, 12GB RAM, 200GB SSD, 300 Mbit/s Port)
    - 공유 환경이므로 CPU를 오래 점유하는 작업은 지양한다 (노이즈 네이버, steal time, sustained turbo 미보장)
  - 가능하다면 메모리는 빠른 조회에 필요한 인프라에 최대한 할당한다

## 4. 기술 선택
### 4.1 외부 API 호출: WebClinet + bounded concurrency
  - 이 서비스의 핵심 부하는 CPU 계산보단 외부 API 호출에 따른 I/O 바운드 작업
  - 저사양 VPS 환경에선 스레드 풀로 많은 블로킹 스레드를 유지하는 방식 보단, 적은 수의 스레드로 동시성을 높이는 방식이 유리하다
    - 특히, 메모리 관점에서 이점
  - 초기 동시성은 30으로 시작하고, 외부 API 응답 시간/실패율/서버 부하를 관찰하며 조정한다

### 4.2 데이터 저장소: MySQL
  - 중복 관리, 인덱스 기반 조회, 보관 정책 관리에 적합하다
  - Outbox 패턴과 함께 트랜잭션 경계를 명확하게 관리할 수 있다

### 4.3 메시지 큐: Rabbit MQ
  - 전체 시스템 규모 상 대규모 이벤트 스트리밍보단 안정적인 전달과 운영의 단순함을 유지하는게 중요하다
  - 저사양 VPS 환경에서도 부담이 적다

### 4.4 기타
  - `Redis`는 초기 버전에서 도입하지 않는다
    - 현재 서비스의 핵심적인 병목은 DB 조회보단 외부 API 호출에서 발생할 가능성이 훨씬 높다
    - 중복 검사는 tafId 유니크 인덱스로도 충분히 처리 가능하다
    - Redis 추가 시 운영 대상이 늘어나고 장애 포인트가 하나 더 추가된다 (즉, 비용대비 이점이 적다)
  - 향후 `Redis` 도입은 아래 상황 발생 시 고려한다
    - 최신 TAF 조회 API가 추가되어 읽기 부하가 증가하는 경우
    - 최신 TAF를 매우 빠르게 응답해야 하는 경우
    - DB 부하 측정 결과, 캐시 이점이 분명한 경우

## 5. 장애 대응 및 신뢰성 전략
### 5.1 외부 API 실패
  - timeout을 설정한다
    - 초기 운영은 평균 응답 시간을 1.5s로 가정한다
    - connect timeout 2s, response timeout 5s로 시작한다
    - 추후 운영 지표를 보며 관리 및 조정한다
  - 개별 공항 호출 실패가 전체 polling 실패로 번지지 않도록 격리한다
  - timeout 및 일시적 5xx 오류ㅜ에 한해 1회 재시도한다
  - 실패 건수, 대상 공항, 오류 원인을 로깅하고 다음 polling 주기에서 다시 수집할 수 있도록 한다

### 5.2 DB 저장 실패
  - 저장과 Outbox 기록은 하나의 트랜잭션으로 묶는다
  - 저장 실패 시 발행도 일어나지 않아야 한다

### 5.3 메시지 발행 실패
  - Outbox 상태를 `FAILED`로 남긴다
  - 별도 publisher가 다시 발행을 시도한다
  - 발행 실패 사유와 횟수를 기록한다

### 5.4 중복 발행
  - at-least-once 모델에선 중복 발행이 발생할 수 있다
  - 따라서 소비자는 idempotency_key를 통해 멱등하게 처리해야 한다
