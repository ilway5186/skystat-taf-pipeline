# SkyStat TAF Ingestion Service

> **실시간 항공 기상 예보(TAF)를 주기적으로 수집하고 중복 없이 저장한 뒤, 다른 서비스에 발행하는 서비스**

## 1. 서비스 목적
실시간 기상 예보(TAF)를 수집하고, 전문의 유효성을 검사한 뒤 저장한다. 그 후 알람 서비스 등 타 서비스에 TAF 데이터를 발행한다

## 2. 역할과 책임
### 2.1 수집
- **역할:** 외부 API를 스케줄링해 최신 TAF 데이터를 수집한다
- **책임**
  - 기본 발부 시각(00Z, 06Z, 12Z, 18Z) 주변에는 집중 수집 시간대(active polling window)를 두고 TAF 데이터를 집중 수집한다
    - 집중 수집 시간대: `HH:00Z ~ HH:40Z`
    - polling 주기: 10분
    - polling 시각 예시: `HH:00`, `HH:10`, `HH:20`, `HH:30`, `HH:40`
    - 목표 완료 시각: `HH:45Z` 이전
    - `HH:40Z`에 마지막 전체 공항 순회를 시작하고, 수집 완료 여유 시간을 5분 둔다
    - 대상 공항은 500~3,000개 내외로 서버 스펙 및 현업 운영 여건에 따라 조절될 수 있다
    - API 동시성은 30으로 시작해 조정해 나간다 (외부 API 서버 RTM 고려)
  - polling 전략은 집중 수집 시간대 기반 전체 공항 목록 순회를 사용한다
    - 외부 API가 `updated-since`방식을 지원하는지 불확실 하므로 기본 전략으로 채택
    - 집중 수집 시간대 외에는 15분 주기의 완화된 polling을 사용한다
    - 목표 완료 시각인 `HH:45Z` 이후에도 발부되지 않은 공항은 공항 기상대 또는 원천 발부 지연일 가능성이 높으므로, 10분 주기로 계속 요청하지 않는다
    - 향후 외부 API가 `updated-since` 방식을 안정적으로 지원하면 증분 수집 방식으로 개선한다

### 2.2 검증
- **역할:** 수집된 TAF 데이터의 유효성을 검증한다
- **책임**
  - 수집된 TAF 응답 데이터가 정상적으로 파싱 가능한지 검증한다
  - 필수 값이 누락되지 않았는지 검증한다
  - TAF 전문 기반으로 고유 식별자인 `TafId`를 생성한다
    - id는 TAF 전문 내용을 기반으로 만든 SHA-256 해시 값이다 (길이 64)

### 2.3 저장
- **역할:** 수집된 TAF 데이터를 저장한다
- **책임**
    - 수집된 TAF 데이터가 이미 저장된 데이터인지 확인한다 (중복 검사)
    - 저장 시 발행을 위한 Outbox 레코드를 함께 기록한다
      - DB 저장과 Outbox 기록을 하나의 트랜잭션으로 처리

### 2.4 발행
- **역할:** 수집된 최신 TAF 데이터를 발행한다
- **책임**
    - 메시지 큐로 수집된 TAF 데이터를 발행한다
      - 최소 한 번 이상은(at least once) 반드시 발행되어야 한다 (→ Outbox 패턴 적용)
    - 발행 시각, 성공 여부, 실패 사유를 기록한다
      - 장애 발생 시 책임 소명을 위해 로깅은 필수
    - 발행 실패 시 재시도 한다

### 2.5 보관
- **역할:** 보관 기간이 지난 TAF 데이터는 삭제(혹은 S3같은 저장소로 이동) 시킨다 
- **책임**
    - TAF 데이터가 보관 기간(1달)을 초과했는지 검사한다
    - 보관 기간을 초과한 데이터는 적절한 조치를 취한다

## 3. 예상 부하 및 인프라 설계 기준
### 3.1 예상 수집 부하
  - 저장되는 TAF 데이터 수와 수집 시도 수는 분리해서 산정한다
    - TAF 데이터 저장량: 일 최대 15,000건 가정
      - 대상 공항: 최대 3,000개
      - TAF 기본 발부(일 4회)와 수정 예보를 고려
    - Retrieval 시도 로그: polling 횟수에 따라 별도로 증가한다

  | 구분 | 하루 예상량 | 초당 평균 |
  |---|---:|---:|
  | 공항별 수집 시도 | 약 300,000~312,000회/day | 약 3.5~3.6회/s |
  | 실제 HTTP 요청 | 약 15,000~15,600 req/day | 약 0.17~0.18 req/s |
  | Retrieval 이력 row | 약 300,000~312,000 rows/day | - |

  - 실제 HTTP 요청량은 chunk size 20 기준으로 산정한다
  - Retrieval 이력에는 TAF 원문을 저장하지 않고, 요청 시각/완료 시각/성공 여부/실패 사유 등 메타데이터만 저장한다
 
### 3.2 서버 환경
  - Contabo VPS20 (6vCPU Cores, 12GB RAM, 200GB SSD, 300 Mbit/s Port)
    - 공유 환경이므로 CPU를 오래 점유하는 작업은 지양한다 (노이즈 네이버, steal time, sustained turbo 미보장)
  - 가능하다면 메모리는 빠른 조회에 필요한 인프라에 최대한 할당한다

## 4. 기술 선택
### 4.1 외부 API 호출: Virtual Threads + bounded concurrency
  - 이 서비스의 핵심 부하는 CPU 계산보단 외부 API 호출에 따른 I/O 바운드 작업
  - 초기 설계에서는 `WebClient` 기반의 non-blocking 방식을 고려했으나, 현재 서비스의 작업 특성상 가상 스레드 기반의 동기 I/O 모델이 더 단순하고 유지보수에 유리하다고 판단한다
    - TAF 수집은 대규모 스트리밍 처리보다는 주기적인 외부 API 호출과 DB 저장 중심의 작업이다
    - 가상 스레드를 사용하면 동기 코드의 직관성을 유지하면서도 I/O 대기 비용을 낮출 수 있다
    - Reactive 프로그래밍 모델로 인해 도메인/애플리케이션 설계의 복잡도가 불필요하게 증가하는 것을 피한다
  - 초기 동시성은 30으로 시작하고, 외부 API 응답 시간/실패율/서버 부하를 관찰하며 조정한다

### 4.2 데이터 저장소: MySQL
  - 중복 관리, 인덱스 기반 조회, 보관 정책 관리에 적합하다
  - Outbox 패턴과 함께 트랜잭션 경계를 명확하게 관리할 수 있다

### 4.3 메시지 큐: Rabbit MQ
  - 전체 시스템 규모 상 대규모 이벤트 스트리밍보단 안정적인 전달과 운영의 단순함을 유지하는게 중요하다
  - 저사양 VPS 환경에서도 부담이 적다

### 4.4 기타
  - 예상 수집량 산정 근거
    - 용어 정의
      - 집중 수집 시간대(active polling window): TAF가 새로 발부될 가능성이 높은 시간대를 정해, 평소보다 더 자주 확인하는 운영 구간이다
        - 예: 06Z TAF는 보통 06:00Z 이후 순차적으로 발부되므로, `06:00Z ~ 06:40Z`를 집중 수집 시간대로 본다
        - 쉽게 말해, "새 예보가 나올 시간대에 집중적으로 확인하는 시간표"다
        - 단, `06:40Z`에 시작한 마지막 수집 작업이 끝날 시간을 고려해 목표 완료 시각은 `06:45Z` 이전으로 둔다
      - 전체 공항 1회 순회(sweep): 관리 대상 공항 전체를 한 번씩 확인하는 한 차례의 수집 작업이다
        - 예: 대상 공항이 3,000개라면, 1회 순회는 3,000개 공항 전체에 대해 TAF 조회를 한 번 시도하는 것을 의미한다
        - 쉽게 말해, "전국/전세계 대상 공항 명단을 처음부터 끝까지 한 번 훑는 작업"이다
        - 외부 API가 여러 공항을 한 번에 조회할 수 있으므로, 1회 순회가 HTTP 요청 1번을 의미하지는 않는다
    - 기본 발부 시각 기준 집중 수집 시간대를 둔다
      - 대상 발부 시각: 00Z, 06Z, 12Z, 18Z
      - 집중 수집 시간대: `HH:00Z ~ HH:40Z`
      - polling 주기: 10분
      - polling 시각 예시: `HH:00`, `HH:10`, `HH:20`, `HH:30`, `HH:40`
      - 목표 완료 시각: `HH:45Z` 이전
      - `HH:40Z`에 마지막 전체 공항 순회를 시작하고, 수집 완료 여유 시간을 5분 둔다
      - 한 집중 수집 시간대당 전체 공항 목록 순회 수: 최대 5회
    - 집중 수집 시간대 외에는 완화된 polling을 사용한다
      - polling 주기: 15분
      - 목적: 기본 발부 이후 늦게 반영된 TAF 또는 수정 예보 감지
      - 목표 완료 시각인 `HH:45Z` 이후에도 미발부 상태인 공항은 원천 발부 지연 가능성이 높으므로 과도하게 재요청하지 않는다
    - 전체 공항 1회 순회의 요청 구성
      - 1회 순회: 대상 공항 3,000개 전체에 대한 조회 시도
      - 외부 API가 여러 공항 id를 한 번에 조회하는 chunk 방식을 지원한다는 전제를 둔다
      - chunk size 20 기준, 1회 순회는 `ceil(3,000 / 20) = 150`개의 HTTP 요청으로 구성된다
    - 일평균 수집 요청량 산정
      - 하루 전체 공항 순회 수: 약 100~104회/day
      - 공항별 수집 시도: `3,000개 공항 * 100~104회 = 약 300,000~312,000회/day`
      - 실제 HTTP 요청: `150 req * 100~104회 = 약 15,000~15,600 req/day`
      - 초당 평균 HTTP 요청량: `15,000~15,600 / 86,400초 = 약 0.17~0.18 req/s`
    - 3,000개 공항 기준 한 집중 수집 시간대의 논리적 수집 시도량
      - `3,000개 공항 * 5회 전체 순회 = 15,000회 공항별 조회 시도/집중 수집 시간대`
      - `15,000 / 2,400초 = 약 6.25회 공항별 조회 시도/s`
    - chunk size 20 기준 한 집중 수집 시간대의 HTTP 요청량
      - 1회 순회: `ceil(3,000 / 20) = 150 req`
      - 한 집중 수집 시간대: `150 req * 5회 전체 순회 = 750 req`
      - 평균 HTTP 요청량: `750 / 2,400초 = 약 0.31 req/s`
    - 초기 동시성 30 기준 예상 1회 순회 완료 시간
      - 평균 응답시간 1.5초: `ceil(150 / 30) * 1.5초 = 약 7.5초`
      - 응답시간 5초: `ceil(150 / 30) * 5초 = 약 25초`
      - 따라서 chunk 기반 요청이라면 10분 polling 주기는 충분히 여유가 있다
    - 공항 1개당 HTTP 요청 1개 방식도 계산상 10분 polling 안에 처리 가능할 수 있다
      - 1회 순회 HTTP 요청 수: 3,000 req
      - 동시성 30, 평균 응답시간 1.5초 기준: 약 150초
      - 동시성 30, 응답시간 5초 기준: 약 500초
      - 단, timeout, 재시도, 외부 API 제한, 네트워크 지연까지 고려하면 운영 여유가 줄어든다
      - 따라서 현재 설계는 chunk 기반 외부 API 호출을 우선 사용해 안정성을 확보한다
  - 가상 스레드의 메모리 이점은 과장하지 않는다
    - 계산 가정
      - Platform Thread stack: 약 1MB/thread (`-Xss1m` 기준 추산)
      - Virtual Thread carrier thread: 서버 vCPU 수와 유사한 6개로 추산
      - Virtual Thread stack chunk: 약 16KB/thread로 추산
    - 동시성 N 기준 예상 스레드 메모리
      - 일반 스레드풀: `N * 1MB`
      - 가상 스레드: `6MB + (N * 16KB)`
      - 예상 절감량: `(N * 1MB) - (6MB + (N * 16KB))`
    - 초기 동시성 30 기준 예상 절감량
      - 일반 스레드풀: `30 * 1MB = 30MB`
      - 가상 스레드: `6MB + (30 * 16KB) ≒ 6.5MB`
      - 절감량: `30MB - 6.5MB = 약 23.5MB`
    - 따라서 현재 설계에서 가상 스레드의 주된 선택 이유는 대규모 메모리 절감이 아니라, I/O 바운드 작업을 동기 코드 형태로 단순하게 유지하면서 향후 동시성 확대 시 Platform Thread 대비 메모리 증가폭을 낮출 수 있다는 점이다
  - `Redis`는 초기 버전에서 도입하지 않는다
    - 현재 서비스의 핵심적인 병목은 DB 조회보단 외부 API 호출에서 발생할 가능성이 훨씬 높다
    - 중복 검사는 tafId 유니크 인덱스로도 충분히 처리 가능하다
    - Redis 추가 시 운영 대상이 늘어나고 장애 포인트가 하나 더 추가된다 (즉, 비용대비 이점이 적다)
  - 향후 `Redis` 도입은 아래 상황 발생 시 고려한다
    - 최신 TAF 조회 API가 추가되어 읽기 부하가 증가하는 경우
    - 최신 TAF를 매우 빠르게 응답해야 하는 경우
    - DB 부하 측정 결과, 캐시 이점이 분명한 경우

## 5. 장애 대응 및 신뢰성 전략
### 5.1 외부 API 실패
  - timeout을 설정한다
    - 초기 운영은 평균 응답 시간을 1.5s로 가정한다
    - connect timeout 2s, response timeout 5s로 시작한다
    - 추후 운영 지표를 보며 관리 및 조정한다
  - 개별 공항 호출 실패가 전체 polling 실패로 번지지 않도록 격리한다
  - timeout 및 일시적 5xx 오류ㅜ에 한해 1회 재시도한다
  - 실패 건수, 대상 공항, 오류 원인을 로깅하고 다음 polling 주기에서 다시 수집할 수 있도록 한다

### 5.2 DB 저장 실패
  - 저장과 Outbox 기록은 하나의 트랜잭션으로 묶는다
  - 저장 실패 시 발행도 일어나지 않아야 한다

### 5.3 메시지 발행 실패
  - Outbox 상태를 `FAILED`로 남긴다
  - 별도 publisher가 다시 발행을 시도한다
  - 발행 실패 사유와 횟수를 기록한다

### 5.4 중복 발행
  - at-least-once 모델에선 중복 발행이 발생할 수 있다
  - 따라서 소비자는 idempotency_key를 통해 멱등하게 처리해야 한다
